## 2. 參考角色的大動作是怎麼撐住的

`big_moves.py`：在 235 隻裡找出四肢骨轉幅 ≥ 60° 的時間軸，共 **1474 段、119 隻角色**，
再看每一段的圖是用什麼方法撐住的：

| 方法 | 佔比 | 說明 |
|---|---|---|
| 跨關節加權網格 | **74.3%** | 同一張圖的頂點同時綁在這根骨和它的父骨上，關節處是彎的，不是一張卡片繞著釘子轉 |
| 動畫中改前後順序 | 40.2% | 手臂轉到身體前面時，前後順序也跟著換 |
| 換圖 | 18.0% | 舉手、縮短透視的拳頭各自另畫一張 |
| deform 關鍵幀 | 6.0% | 逐頂點修形 |
| IK | 4.7% | |
| transform 約束 | 2.2% | 假透視 |
| **都沒有（剛性片硬轉）** | **17.0%** | 多半是道具、翅膀、尾巴這類本來就是硬的東西 |

大動作的時間軸上，key 數的中位數是 9（p25 5、p75 14）：大動作並不靠密集的 key，靠的是圖撐得住。

## 3. 猴子的瓶頸（依影響大小排序）

1. **美術是單一姿勢的剛性切件。** 前臂連手是一張 129×259 的圖，中心離關節很遠；上臂是一整塊上寬下窄的毛。
   產生器自己掃角度量出來：肩膀 25° 還好、30° 變僵、40° 離開衣服、50° 像木板，所以寫死 `MAX_SHOULDER 26`、`MAX_ELBOW 22`
   （`generate_monkey_spine.mjs` 第 465–560 行）。參考角色的大動作有 83% 至少用了一種撐圖的方法，猴子的手和前臂一種都沒有。
2. **被擋住的地方沒畫。** 切圖時只往下延伸 26 px（`UNDERLAY`）補邊色。Iron Jaw 每隻切 17–20 塊，
   每塊被擋住的部分都畫完整；Hard Time 為此另外生了 8 張補畫圖（P1–P4、W1–W4）。沒有完整的底圖，
   一動大就露洞或露出殘影，最後只能把角度壓小。
3. **沒有 IK，腿不能動。** 猴子的 README 明寫「腿不動」，身體的上下起伏只能靠平移整個髖部，
   沒辦法讓膝蓋彎、重心下沉或前衝。Iron Jaw 的 `body` 上下 18（約畫面高 4%），腳靠 IK 釘住，膝蓋自己彎；
   出拳時身體往前 42。
4. **大姿勢沒有換圖、也不換前後順序。** 雙手舉過頭、拳頭打向鏡頭，這些都需要另一張圖或換順序。
   產生器的註解自己也承認「這要上臂另外畫一張，是美術的事」，但流程裡沒有任何一步會去要這張圖。
5. **動作是手寫關鍵幀再平滑。** 時間結構大致合理（`LEAD 0.05`、`DRAG 0.08`），但每段的「蓄力 → 出手 → 停 → 收」沒有被當成規則。
   Iron Jaw 的 `active`：0–0.333 秒蓄力，**0.333–0.433 秒只用 0.1 秒打出去**，0.433–0.667 秒停住，0.667–1.0 秒收回，
   再用 0.17–0.2 秒混回全域時鐘上的待機。順暢靠的是：待機只 key 9–13 根骨頭（每根 2–4 個 key），
   其他的交給 physics 和 IK 算；每往外一節就晚 0.067 秒到極值。

## 4. Hard Time 為什麼還不夠

結構已經照 Iron Jaw 改了：每層都是加權網格、四段腿 IK、physics、共用時鐘、相位相反。但是：

- **動作仍然很小**：囚犯四肢最大只轉 3.4°（雙手交叉，本來就動不了），典獄長除了警棍揮擊以外，手臂只在 2–12° 之間。
- **關鍵幀是 30 fps 線性取樣**（`sample()` → 每秒 300+ 個 key，0% bezier）：動作是對的，但檔案大，
  在 Spine 編輯器裡也沒辦法手調，而且 0.1 秒的出手只有 3 個取樣點。
- **姿勢本身就不適合大動作**：交叉雙手、警棍扛在身後，這些都是「動作預算」在選角色時就決定好的。

結論：**「結構對」只完成一半。** 另一半是美術能不能撐大角度（補畫、換圖），以及動作是否照規則設計（節拍、延遲、overshoot）。
這兩件事都得做進生成器，不能靠事後手調。
